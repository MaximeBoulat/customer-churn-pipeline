Three systems and the S3 layout they share. Each section below covers one part at a glance; the detailed diagram at the bottom is the reference and shows every artifact and edge at once.

System 1: train and deploy

Run on demand as a SageMaker Pipeline. Two levels: a data track that curates and prepares, then a model track that fits, judges and releases. The hand-off is the Feature Store; the exit is an approved model package.

Orchestration

The stages below are the steps of one SageMaker Pipeline, cell2cell-churn-pipeline, registered by infrastructure/terraform/pipeline and generated by scripts/build_pipeline_definition.py. The DAG is what makes the ordering, the branch and the failure behaviour explicit rather than a convention between scripts.

Stage Step Type
catalog not in the DAG; infrastructure/terraform/data-catalog —
processing Cell2CellProcess Processing
feature_store Cell2CellFeatureStore Processing
training Cell2CellTrain Training
evaluation Cell2CellEval Processing
gate Cell2CellQualityGate Condition
registration Cell2CellRegister / Cell2CellQualityGateFailed RegisterModel / Fail

Training runs the image and hyperparameters infrastructure/terraform/train-model/scripts/train.py uses, so the DAG and that script train the same model rather than two configurations of one.

The step contract, including what each step reads and writes, is docs/m4-04-pipeline-contract.md.

Two limits worth stating. Only the Processing steps run code of ours, so training, registration and gate cannot record themselves in the execution manifest and stay pending on a successful run. And the DAG does not publish a preprocessing contract, so bumping PREPROCESSING_CONTRACT means running infrastructure/terraform/feature-store's ingest first.

System 2: operational serving

Weekly, and the system demoed for Module 7. It reads the approved package and the preprocessing contract that package was fitted with — never a reimplementation of the transform, which is what keeps training and serving consistent.

System 3: observability

Reads what System 2 scored, and the labels that arrive later, to decide whether the model still behaves. Sustained drift prompts a retrain, which is a human decision rather than an automated edge.

Storage

One bucket, one prefix per stage, each versioned on its own axis. A run is reconstructible from its execution manifest alone.

Prefix Keyed by Holds
raw/ cell2cell/ source CSVs, provenance.json
curated/ cell2cell/{curation-version}/ partitioned Parquet, split=train and split=holdout
preprocessing/ cell2cell/{preprocessing-contract}/ preprocessing_parameters.json, published per contract version, not per run
features/ cell2cell/{feature-version}/ Feature Store offline store
models/ cell2cell/{model-version}/{execution-id}/ model artifact, evaluation report
inference/ cell2cell/{run-id}/ scored output
monitoring/ cell2cell/{run-id}/ baseline, analysis report
pipeline/ {execution-id}/ execution_manifest.json, the run's split CSVs and its fitted contract

pipeline/ is the odd one out: it is keyed by execution rather than by dataset, because it records a run rather than an artifact. Every stage updates the same manifest in turn.

models/ carries the execution id under the version because a model artifact and its evaluation report belong to the run that produced them. Keying on the version alone means each run silently replaces the last one's evidence, which breaks the guarantee above that a run is reconstructible from its manifest.

preprocessing/ is the exception: it is published once per contract version, because System 2 reads it to score with the same transform training used. A run keeps its own fitted copy under pipeline/{execution-id}/, and replaces the published contract only when the contract version is deliberately bumped. Rewriting it per run would change what an already-released model is scored with.

pipeline/{execution-id}/execution_manifest.json (src/manifest.py) is the single record mapping one execution to the exact artifact versions it used and produced.

used holds the four version axes for the execution, sourced from src/config.py at creation and fixed for the life of the run. update_manifest(execution_id, stage, status, **produced_fields) merges each stage's own fields into produced as a flat dict.
