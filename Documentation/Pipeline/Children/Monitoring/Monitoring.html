Feature overview

System 3 examines the completed outputs of Batch transform. It asks whether the input features have changed, whether predictions remain useful when actual churn labels arrive, and whether outreach differs between credit-rating groups. It publishes a report to S3 and summary metrics to CloudWatch.

The calculations run locally. This follows PR #56's monitoring approach; it does not provision a SageMaker monitoring job, change the approved cutoff or retrain the model.

Analyze a completed batch

Overview

The batch's manifest.json identifies its approved contract and training execution. On the first monitoring run for that execution, the script reads its training CSV and saves a baseline. Later batches reuse that baseline.

Population Stability Index (PSI) compares the proportion of records in each feature bin: training proportions p_i against batch proportions q_i. Numeric features use fixed bins; binary and other low-cardinality features use value counts. A small smoothing value avoids division by zero.

\mathrm{PSI}=\sum_i(q_i-p_i)\ln\left(\frac{q_i}{p_i}\right)

PSI below 0.1 is treated as stable, 0.1 to below 0.2 as a warning, and 0.2 or above as an investigation signal. Drift describes changed input distributions; it does not by itself prove worse predictions.

With labels, the script joins customerid,churn_label to the batch's existing outreach flags. It records match coverage, the confusion matrix, precision, recall, F1, F2 and accuracy. It neither selects a new cutoff nor adjusts the scores.

The labelled subset also supports a credit-rating comparison: the first category in the pinned encoding is the reference group, compared with all remaining categories. DI is the other group's flag rate divided by the reference group's flag rate. The report also records differences in flag rate (DPPL), recall (RD) and accuracy (AD). These are investigation signals, not a declaration of fairness. The group is reconstructed from encoded features, so an unseen category encoded as all zeros is indistinguishable from the reference category.

The current holdout has no labels, so ordinary monitoring reports drift and outreach counts only. An optional replay uses the pinned model on its already-held-out test split and supplies its known labels. This demonstrates quality and group measurements; it does not provide new production outcomes. Replay metrics are separated from live metrics.

Publish the report and metrics

Overview

The script writes drift_report.json, then publishes aggregate metrics under churn-rebuild/ChurnMonitoring. Despite its filename, the report includes drift, outreach counts, label coverage, quality and group comparisons. Quality and bias are null when labels are unavailable.

The dashboard displays separate Source=live and Source=replay series. The operator investigates the report before deciding whether another training run is warranted.
