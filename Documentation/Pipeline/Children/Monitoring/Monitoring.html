Feature overview

Monitoring takes the following forms:

  • Has the distribution of the data changed against the distribution that the model was trained on (Population Stability Index: PSI)?
    • This matters because generalization was demonstrated on particular data, so the confidence level in the model's ability to predict things correctly decreases if the data distribution shifts significantly.
  • Model quality
    • Established by comparing the model's accuracy/precision/recall/MSE etc. against the baseline.
  • Disparate Impact Assessment
    • Assesses whether different customer groups are being treated fairly by the model.
  • Inference
    • We can key off the latest inference run to do some glaring anomaly detections like sudden spikes or drops in the number of flagged customers.

Data distribution analysis

Dashboard display What it measures How to interpret it
Biggest shift (PSI) The largest Population Stability Index among the compared features. PSI measures how much a feature’s distribution differs from the baseline. Below 0.1: little change. From 0.1 to below 0.2: a change to watch. At least 0.2: investigate.
Features past 0.2 The number of features whose PSI is at least 0.2. Zero means none of the compared features reached the investigation threshold.
Biggest shift, run by run The history of the maximum PSI measurement. Shows whether the largest feature shift is increasing or decreasing over time.

Model quality analysis

Dashboard display What it measures How to interpret it
Precision and recall, % — precision Among flagged customers with known churn labels, the percentage who actually churned. Higher means fewer false alarms among the customers flagged.
Precision and recall, % — recall Among customers who actually churned, the percentage the model flagged. Higher means fewer churners were missed.
F2, % A combined precision-and-recall score that gives more weight to recall. Higher is better. The configured quality alarm threshold is 0.17%.
F2, run by run The history of F2 measurements, displayed as percentages. Shows whether this measure of model quality is improving or deteriorating.

Disparate impact analysis

Dashboard display What it measures How to interpret it
Fairness ratio The flag rate for customers outside the highest credit-rating group relative to the flag rate for customers in that group. 1 means equal flag rates. Above 1 means the other customers are flagged more often; below 1 means less often. The configured investigation band is 0.8–1.25.
Assessed this run Whether the run met the minimum of 20 flagged customers for the fairness comparison. 1 means assessed; 0 means not assessed. Zero does not mean the model is fair.
Fairness ratio, run by run The history of the flag-rate ratio. Shows how the disparity changes over time relative to the 0.8 and 1.25 boundaries.

Inference analysis

Dashboard display What it measures How to interpret it
Scored The number of customers given a churn prediction. The size of the inference batch.
Flagged for a call The number of customers selected for contact. The number of customers the retention team would contact.
Flag rate The percentage of scored customers selected for contact. How large a share of the batch is flagged.
Outcomes known The percentage of scored customers matched to a known actual churn label. 100% means every scored customer has a matched label. A blank display means no label-coverage measurement was published.

Alarms

The dashboard’s Right now panel displays five alarm states.

Alarm What it checks When it turns red
drift The maximum feature PSI. PSI is at least 0.2.
quality F2. F2 falls below 0.17%.
bias The fairness comparison. An assessed comparison reports a breach of the 0.8–1.25 band.
nobody-flagged Whether any customers were selected for contact. A batch flags zero customers.
stale Whether monitoring is still publishing successful runs. No successful monitoring measurement is available across seven daily periods.

A blank measurement is not a zero. A green alarm means its configured condition is not in alarm; it does not establish that every measurement was available.

How it works

  1. Read the inputs. Read the completed inference batch, the baseline for comparisons that need it, and actual churn labels when available.
  2. Generate the report. Calculate the measurements and save the monitoring report.
  3. Publish the measurements. Send them to CloudWatch. The dashboard displays them and the alarms evaluate them. Refreshing the dashboard shows the published results; it does not recalculate them.

Analyze a completed batch

Overview

The operator first supplies a training execution to fit the baseline. This writes the feature-version baseline; later monitoring runs load it. The script reads a completed batch’s manifest, scores and features, calculates feature PSI and flag rate, and compares credit-rating flag rates across all scored customers. Supplied labels additionally enable model quality and per-credit-rating performance results.

Labels are selected explicitly, including for replay. The script does not automatically read a labels URI from the manifest. Without labels it skips model quality and per-group performance, but still calculates disparate impact; a supplied labels file with no matching customers causes quality calculation to fail. Fairness flags scores at or above the threshold; model quality retains the existing strictly-above comparison.

The optional replay selects an execution, registry version and split, loads that execution’s model, and uses its evaluation cutoff unless overridden. It can multiply a chosen feature by a supplied factor to simulate drift. It writes a separate batch with replay: true, simulation metadata when applicable, and positional IDs such as t00000. Those IDs match within the replay’s files; they are not real customer IDs. This matches the reference code, despite its accompanying document saying otherwise.

Publish the report and metrics

Overview

The report is written before aggregate metrics are published to churn-rebuild/ChurnMonitoring. All runs share the ModelName=churn-rebuild dimension. Replay and simulation flags remain in the report’s manifest; CloudWatch does not separate them. A replay therefore also contributes to the freshness alarm.

Per-feature PSI, confusion counts, subgroup details and DPPL/RD/AD remain in the S3 report. CloudWatch receives the aggregate metrics identified in the first table; undefined values are omitted. Publishing metrics does not launch a new pipeline execution.
