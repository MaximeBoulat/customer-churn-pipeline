Feature overview

Read this feature as the continuation of : System 2 declares six monitoring needs; System 3 consumes its completed batch outputs and implements the calculations below.

The reference is Dennis’s PR #56 at 0740804. The personal monitoring code now follows that implementation, including its limitations. The same six requirements appear in the same order on both pages. The contract calls its monitoring list “for orientation”; its rule to consume the existing outreach flag is explicit.

In the table, batch files are inference/cell2cell/<run-id>/{manifest.json,scores.csv,features.csv}. “Report” means monitoring/cell2cell/<run-id>/drift_report.json. All paths below use the personal bucket s3://customer-churn-pipeline-a81b79/ unless identified as team paths.

System 2 expectation System 3 calculation Input sources Result, dashboard and alarm Coverage / limitation
1. PSI per feature against a reference window \mathrm{PSI}=\sum_i(q_i-p_i)\ln(q_i/p_i) compares reference proportions p_i with batch proportions q_i. Both are floored at 10^{-6}. Numeric bins use training quantiles; text features use categories. Batch features.csv and saved baseline.json. Dennis fits the baseline from a republished training split; our storage adapter reads the original split. Report drift.psi contains each feature. CloudWatch receives MaxFeaturePSI, FeaturesWarning, FeaturesInvestigate. Dashboard shows maximum PSI and investigation count; drift alarm fires at PSI ≥ 0.2. Implemented with a limitation: constant numeric features are omitted, and some binary distributions collapse into one bin, producing PSI 0 even after a large change.
2. Score drift No score-distribution comparison is calculated. scores.csv → churn_probability is available, but there is no reference score distribution. No report field, dashboard chart or alarm. Not implemented. Feature PSI and flag rate do not measure score drift.
3. Flag rate flagged = sum of stored outreach_flag; rows = number of score rows; flag rate = flagged / rows. Batch scores.csv → outreach_flag and manifest.json → flagged. Report flags includes counts, rate, agreement with manifest and a zero-flag indicator. CloudWatch/dashboard show scored, flagged and flag rate. NobodyFlagged drives an alarm. Partially fulfilled: no expected-rate comparison or explicit fallback treatment for threshold.outreach_policy=top_k.
4. Model quality when labels arrive later Join labels by customer ID, then recompute predictions as churn_probability > threshold.value. Count TP, FP, FN, TN. Precision = TP/(TP+FP); recall = TP/(TP+FN); accuracy = (TP+TN)/N. F_\beta=\frac{(1+\beta^2)PR}{\beta^2P+R} gives F1 and F2, with P = precision and R = recall. Batch scores.csv → customerid, churn_probability, manifest.json → threshold.value and explicitly supplied labels CSV customerid, churn_label. Report quality contains confusion counts, accuracy, precision, recall, F1, F2 and labelled predicted-positive rate. label_join records match coverage/counts. CloudWatch publishes the five quality metrics and coverage; dashboard shows precision, recall, F2 and coverage. F2 alarm: below 0.0017. Metrics exist, but the contract explicitly requires reading stored outreach_flag. Recomputing with > differs from System 2’s ≥. Undefined F1/F2 can be omitted rather than reported as zero.
5. Bias slices Reconstruct credit rating from one-hot columns. Compare reference group A (default 1-highest) with others D: DI=r_D/r_A, DPPL=r_A-r_D, plus recall difference RD and accuracy difference AD. Also calculate quality for each individual credit-rating category when it has ≥100 rows and both labels. The labelled score join from row 4 plus features.csv → creditrating__…. Recomputed predictions are used here too. There is no join to curated demographic columns. Report bias and subgroups. CloudWatch publishes DI_CreditRating, FourFifthsBreach, BiasAssessed when applicable; dashboard shows DI and assessment status. Bias requires ≥20 flagged labelled rows; DI outside 0.8–1.25 triggers the alarm. Different scope: credit rating only, reconstructed from encoded features. An undefined DI can count as a breach. The band is a screening signal, not proof of fairness.
6. Baseline per model Persist reference bins/categories, proportions and version metadata under the configured feature version. Later runs reuse that file. Operator-supplied training execution and configured CURATED_VERSION, PREPROCESSING_CONTRACT, MODEL_VERSION, FEATURE_VERSION. Dennis does not use the batch’s package ARN/contract checksum to validate baseline identity. monitoring/cell2cell/<feature-version>/baseline.json. Baseline identity is not a dashboard metric. Not fulfilled as a per-model association: multiple models with the same feature version share the baseline location; fitting again replaces it.

TP, FP, FN and TN are true positives, false positives, false negatives and true negatives. A positive label means actual churn. Group flag rate is denoted by r. Quality and bias require supplied labels; the live holdout has none. Dennis’s optional labelled replay demonstrates these calculations on a training/validation/test split; it is not new production ground truth.

Supporting metrics are JobSucceeded (1 on a successful monitoring run), scored/flagged counts, and label coverage (matched/scored), with missing and unmatched label counts in the report. The fifth alarm checks for no successful monitoring measurement across seven daily periods. No explicit failure metric is published.

Reference code: calculations and metric payload, run orchestration, and dashboard. Their local counterparts are monitoring/metrics.py, monitoring/run_monitoring.py and monitoring/dashboard.json.tftpl.

Component analysis

Diagram

Key AWS actors and concepts

S3 stores the batch files, baseline and report. CloudWatch stores aggregate metrics, displays them on a dashboard and checks alarm thresholds. The calculations run locally; there is no SageMaker monitoring job.

Sequence analysis

Provision monitoring

Overview

Terraform creates the dashboard and five alarms: feature drift, F2, credit-rating disparity, nobody flagged and stale monitoring. It does not schedule monitoring or retrain the model. There are no notification actions.

The F2 floor of 0.0017 comes from Dennis’s measured runs; it has not been calibrated to our model. All alarms except freshness treat missing data as not breaching. The copied dashboard’s “everything is fine” wording must not be read as evidence that quality or bias was measured: an unlabeled batch supplies neither.

Analyze a completed batch

Overview

The operator first supplies a training execution to fit the baseline. This writes the feature-version baseline; later monitoring runs load it. The script reads a completed batch’s manifest, scores and features, calculates feature PSI and flag rate, and optionally joins supplied labels for quality, bias and per-credit-rating subgroup results.

Labels are selected explicitly, including for replay. The script does not automatically read a labels URI from the manifest. Without labels it skips quality/bias; a supplied labels file with no matching customers causes quality calculation to fail. It recomputes decisions from probabilities for quality/bias as described in row 4 above.

The optional replay selects an execution, registry version and split, loads that execution’s model, and uses its evaluation cutoff unless overridden. It can multiply a chosen feature by a supplied factor to simulate drift. It writes a separate batch with replay: true, simulation metadata when applicable, and positional IDs such as t00000. Those IDs match within the replay’s files; they are not real customer IDs. This matches the reference code, despite its accompanying document saying otherwise.

Publish the report and metrics

Overview

The report is written before aggregate metrics are published to churn-rebuild/ChurnMonitoring. All runs share the ModelName=churn-rebuild dimension. Replay and simulation flags remain in the report’s manifest; CloudWatch does not separate them. A replay therefore also contributes to the freshness alarm.

Per-feature PSI, confusion counts, subgroup details and DPPL/RD/AD remain in the S3 report. CloudWatch receives the aggregate metrics identified in the first table; undefined values are omitted. Publishing metrics does not launch a new pipeline execution.
