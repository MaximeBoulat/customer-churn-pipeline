Feature overview

The data catalog stage registers the raw cell2cell CSV in Glue, then uses Athena to curate it into a typed, partitioned Parquet table and a training-ready view. It is a one-shot batch construction: once curated, the raw table is never read again.

Sequence analysis

Provision and curate data

Overview

  1. Terraform creates the Glue database (the catalog namespace).
  2. Terraform creates the cell2cell_raw external table over the raw CSV in S3. This is schema-on-read: OpenCSVSerde parses the quoted CSV, every column is typed STRING, and no data is moved.
  3. Terraform creates the Athena workgroup, which sets the query result output location (distinct from the table's own LOCATION).
  4. The operator runs run_curation.py, which submits 01_create_curated.sql to Athena.
  5. Athena resolves the raw table's schema from Glue, reads the raw CSV from S3, and executes the CTAS: casting every column to its real type, deriving churn_label and split, and writing the result as Parquet (partitioned by split) to a new S3 location.
  6. The CTAS registers the new cell2cell_curated table in Glue. cell2cell_raw was only ever read by this one query and is not used again.
  7. run_curation.py submits 02_create_view.sql, which creates vw_cell2cell_training — a view over cell2cell_curated filtered to split = 'train' with a non-null churn_label.
Why materialize to Parquet instead of querying the raw CSV directly

Athena bills by bytes scanned per query. OpenCSVSerde reads full rows as uncompressed text with no partition pruning, so every query against cell2cell_raw scans the entire raw CSV. Snappy-compressed, partitioned Parquet reduces the bytes scanned per query, which lowers both cost and latency — this is the performance gain.

It is not only a performance question. OpenCSVSerde can only reliably return STRING columns; real types only exist once the CTAS applies its explicit CASTs. A view over the raw table would still be all-STRING.

A view is also not materialized: every query against it would re-read the raw CSV and re-run its SELECT logic, including the casts and the derived churn_label/split columns, on every call. CTAS turns that recurring per-query cost into a one-time cost paid once, at curation time, instead of on every downstream query.

Artifacts and effects analysis

Versioned processes and outputs

CURATED_VERSION identifies the schema version of both the external table over the raw CSVs and the CTAS that produces the curated dataset. When those schemas change, the version is bumped and the curated output goes into the corresponding S3 folder: curated/cell2cell/{version}/.

Current implementation limitation: Terraform can be applied again, but the curation script cannot recreate an existing cell2cell_curated table or write into an occupied CTAS destination. Changing CURATED_VERSION from v1 to v2 selects a new S3 folder, but the fixed table name still exists. Terraform updates the existing raw-table definition rather than creating a separately versioned table.

The versioning plan therefore needs a catalog-update procedure, which is not implemented yet. One approach is to keep stable table names, update the raw schema, and recreate the curated table's catalog definition for the new version while retaining the old Parquet under v1/.
