Feature overview

The SageMaker pipeline starts from curated labeled Parquet. It runs preprocessing and Feature Store ingestion, trains XGBoost, evaluates it on the test split, and registers a model only when its AUC passes the quality gate. A registered model starts as PendingManualApproval; this does not approve or deploy it.

Component analysis

Diagram

Key AWS actors and concepts

SageMaker Pipelines coordinates jobs and records each execution. Training jobs fit models on temporary compute. A model package group holds registered model versions; each package points to a trained artifact and its inference image.

SageMaker Processing runs the preprocessing and ingestion scripts. A Feature Group defines feature records; its offline store writes them to S3 asynchronously. The online store is disabled.

Preprocess

Overview

  1. Read curated/cell2cell/{CURATED_VERSION}/split=train/ directly. The Athena training view is not used.
  2. Assign customers deterministically to approximately 70% training, 15% validation and 15% test, separately within each class. A customer must occur once. The fixed seed is 540.
  3. Exclude the three leakage columns and keep IDs, labels and partition information out of model features.
  4. Treat zero ages as missing. Add flags for zero ages, missing handset price, and an entirely missing usage record.
  5. Fit numeric medians, ServiceArea frequencies, and categorical levels on training rows only. Apply those values to every split. Other categorical fields are one-hot encoded with the first sorted category omitted.
  6. Write headerless, label-first CSVs, corresponding customer IDs, and preprocessing_parameters.json containing the fitted transformation and feature order.

Unseen ServiceArea values map to zero; unseen one-hot categories produce all zeros. Entirely missing numeric training columns use zero instead of a median. No probability recalibration is fitted here; the saved factor is 1.0.

Evaluate

Overview

The model emits raw scores for validation customers. Evaluate chooses a cutoff using those scores and the known validation labels, then applies that fixed cutoff to test predictions to calculate the confusion matrix, precision, recall, F1 and accuracy. The test results do not influence the cutoff. ROC-AUC is calculated across thresholds from the test scores; the quality gate checks AUC independently of the selected cutoff.

Choosing the cutoff. At each candidate cutoff, TPR is the fraction of churners flagged and FPR is the fraction of non-churners flagged. The calculation assumes 2% churn in production, $500 per missed churner and $100 per contact, including correctly contacted churners. Estimated cost per customer is:

C(t)=0.02[1-\mathrm{TPR}(t)]\,500+0.02\,\mathrm{TPR}(t)\,100+0.98\,\mathrm{FPR}(t)\,100

The selected cutoff minimizes this cost on validation. Contacting nobody is also a candidate, costing 0.02\times500=10 dollars per customer. Equal-cost ties favor fewer contacts. These are illustrative assumptions: the calculation treats contacting a churner as avoiding the $500 loss, without separately modeling whether the offer succeeds.

If contacting nobody is cheapest, the team's policy overrides that choice: use the 95th percentile of validation scores by default, targeting approximately the highest-scoring 5%. The fraction is configurable through Terraform's outreach_top_k variable (default 0.05). The report retains contact_nobody=true and records outreach_policy="top_k", the fallback's cost and the no-contact cost. This fallback is not cost-optimal. Its fixed cutoff carries forward; it does not guarantee that 5% of test or production customers are flagged.

Why prevalence matters. The supplied training population contains roughly 28.8% churners. Its confusion-matrix counts therefore do not describe a production population with 2% churn. The cost calculation uses validation TPR and FPR, weighted by 2% churners and 98% non-churners. This assumes those conditional rates carry over to production.

Bayesian interpretation: probabilities versus decisions. A fixed trained model gives the same score for the same features. But the probability learned during training depends on how frequently churn occurs among customers with those features. Bayes' rule expresses this as:

\frac{P(Y=1\mid x)}{P(Y=0\mid x)}=\frac{P(x\mid Y=1)}{P(x\mid Y=0)}\frac{\pi}{1-\pi}

Here \pi=P(Y=1) is prevalence. If sampling changes only the class proportions, leaving the feature distribution within each class unchanged, calibrated sample probabilities could be adjusted to production probabilities using:

k=\frac{\pi_{\mathrm{prod}}/(1-\pi_{\mathrm{prod}})}{\pi_{\mathrm{sample}}/(1-\pi_{\mathrm{sample}})},\qquad p_{\mathrm{prod}}=\frac{k\,p_{\mathrm{sample}}}{1-p_{\mathrm{sample}}+k\,p_{\mathrm{sample}}}

For 2% versus 28.8%, k\approx0.0505; a sample probability of 0.80 would become about 0.168. This changes the probability scale, not customer ranking. Applying the same monotonic transformation to both scores and cutoff would preserve the contact decisions.

This probability adjustment is not implemented here or in the team's current pipeline. Recalibration remains 1.0. The implemented method leaves scores unchanged and accounts for prevalence in the cost calculation used to choose the cutoff. Passing the AUC gate does not establish that contacting customers is economically beneficial.

Quality gate

Overview

The gate compares test AUC with TF_VAR_auc_threshold, currently 0.60. Passing permits registration; failing ends the execution without registering a package. This is independent of the classification cutoff selected on validation and used in evaluation.

Artifacts and effects analysis

Versioned processes and outputs

No new artifact version is created. The pass/fail result is recorded in the pipeline execution.

└─ …

Register model

Overview

A passing model is registered as PendingManualApproval. The package references the trained artifact, its inference image, the evaluation report and the fitted preprocessing parameters. Registration does not approve or deploy the model.
