Feature overview

The SageMaker pipeline starts from curated labeled Parquet. It runs preprocessing and Feature Store ingestion, trains XGBoost, evaluates it on the test split, and registers a model only when its AUC passes the quality gate. A registered model starts as PendingManualApproval; this does not approve or deploy it.

Component diagram

Key AWS actors and concepts

SageMaker Pipelines coordinates jobs and records each execution. Training jobs fit models on temporary compute. A model package group holds registered model versions; each package points to a trained artifact and its inference image.

SageMaker Processing runs the preprocessing and ingestion scripts. A Feature Group defines feature records; its offline store writes them to S3 asynchronously. The online store is disabled.

Sequence diagram

Infrastructure versus execution

terraform apply in pipeline/ uploads four Python files to S3 and creates or updates the Feature Group, model package group and pipeline definition together. The definition is written once in definition.tf; Terraform converts it to JSON. There is no generator, copied JSON template, separate train-model stack or second Feature Store stack.

run_pipeline.py starts an execution and prints its ARN. The jobs run in AWS and continue after the local command exits. Applying Terraform does not start a run; starting a run does not reapply Terraform.

Preprocessing

  1. Read curated/cell2cell/{CURATED_VERSION}/split=train/ directly. The Athena training view is not used.
  2. Assign customers deterministically to approximately 70% training, 15% validation and 15% test, separately within each class. A customer must occur once. The fixed seed is 540.
  3. Exclude the three leakage columns and keep IDs, labels and partition information out of model features.
  4. Treat zero ages as missing. Add flags for zero ages, missing handset price, and an entirely missing usage record.
  5. Fit numeric medians, ServiceArea frequencies, and categorical levels on training rows only. Apply those values to every split. Other categorical fields are one-hot encoded with the first sorted category omitted.
  6. Write headerless, label-first CSVs, corresponding customer IDs, and preprocessing_parameters.json containing the fitted transformation and feature order.

Unseen ServiceArea values map to zero; unseen one-hot categories produce all zeros. Entirely missing numeric training columns use zero instead of a median. No probability recalibration is fitted here; the saved factor is 1.0.

Feature Store ingestion

ingest.py waits for the group to be ready, checks its schema against the processed features, and sends every train, validation and test row through PutRecord. It adds the customer ID, label, split name, execution ID and event time. An ingestion error fails the step and blocks training.

A successful step means all records were accepted by the API. Delivery into offline S3 files happens later. Training reads the processed CSVs directly, so it does not wait for that delivery or query Feature Store. Repeated executions append feature history; execution_id distinguishes their records.

Training, evaluation and registration

Preprocess → IngestFeatures → Train → Evaluate → QualityGate → RegisterModel or Fail

Training waits for successful ingestion but reads preprocessing's CSVs directly. Validation is supplied to XGBoost to report metrics during training; this implementation uses a fixed 100 rounds and does not tune parameters. The test split is used only by evaluation.

Classification threshold 0.5 converts test probabilities into labels for precision, recall, F1, accuracy and the confusion matrix. AUC threshold 0.60, configured in .env, determines whether registration is allowed. These are different thresholds. Recalibration remains 1.0; no cost-based threshold selection is fitted.

The registered package uses exactly the training image and artifact. Its metadata includes the S3 URI of this execution's fitted preprocessing contract. It does not provide a production approval or serving workflow.

Versioned processes and outputs

  • CURATED_VERSION selects the source Parquet directory.
  • PREPROCESSING_CONTRACT identifies transformation rules. Each execution saves its own fitted parameters under pipeline/{execution-id}/process/contract/.
  • FEATURE_VERSION identifies the Feature Group schema and appears in its name and offline prefix.
  • MODEL_VERSION identifies the model configuration and selects models/cell2cell/{version}/{execution-id}/.

These values come from exported TF_VAR_* settings and are embedded when Terraform updates the pipeline. Reloading .env alone does not change the registered definition. SageMaker assigns a separate numeric package version on successful registration.

Before a run, infrastructure exists but the execution's outputs do not. After success, it has processed splits, fitted parameters, accepted feature records, a model, an evaluation report and a pending package. A failed AUC gate retains outputs but creates no package. SageMaker records execution status; there is no additional manifest.

Run from the repository root

Prerequisites: stage 1 has produced curated Parquet; Learner Lab credentials are current; the existing SageMaker bucket named in TF_VAR_offline_store_bucket exists; LabRole can access both buckets and SageMaker. No bucket or IAM role is created here. The configured XGBoost image is for us-east-1.

set -a
source .env
set +a
uv sync
terraform -chdir=pipeline init
terraform -chdir=pipeline plan
terraform -chdir=pipeline apply
uv run python pipeline/run_pipeline.py

Review the plan before applying. uv sync updates the dependency lock normally. For another model run, repeat only the last command. In SageMaker Studio, open Pipelines → churn-rebuild-pipeline to see the DAG and step results. Registered candidates are under model package group churn-rebuild-models.

Processing and training compute stop when their jobs finish. The Feature Group, model package group, pipeline definition and S3 files remain. No endpoint is deployed.

Implementation status: authored but not executed or validated against AWS. No Terraform, training, ingestion or tests have been run for this implementation.

Files and operation

preprocess.py contains the transformation; process.py reads and writes job files; ingest.py sends records. The pipeline calls these files directly. There is no second ingestion path.

When the feature schema changes

The checked-in feature-store/schema.json starts from the team's existing 70-feature schema. All model features are stored as Fractional values to preserve median-imputed values; five additional fields describe each record. If preprocessing changes the emitted fields, regenerate the schema from real curated data and bump FEATURE_VERSION before applying Terraform. The ingestion step rejects a mismatch rather than silently dropping fields.

The Feature Group persists across runs. Bumping the feature version changes its name and replaces the group managed by Terraform; its old offline S3 files remain.

From the repository root, with .env exported, download the actual curated labeled files and regenerate the schema. These are real data operations, not tests. Then bump TF_VAR_feature_version in .env, reload it, and review the pipeline Terraform plan.

uv sync
aws s3 cp "s3://${TF_VAR_output_bucket}/curated/cell2cell/${TF_VAR_curated_version}/split=train/" data/schema-input/ --recursive
uv run python feature-store/generate_schema.py --curated-directory data/schema-input

Use an empty local input directory for a new curated version so old files are not mixed in. The initial schema is carried from the team implementation; it has not been regenerated or executed in this repo yet.
