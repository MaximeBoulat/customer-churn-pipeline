Feature overview

System 2 applies an approved model to the unlabeled holdout. It reuses the pinned preprocessing, runs SageMaker Batch Transform, and compares each raw score with the pinned evaluation cutoff to produce an outreach flag. It publishes customer scores and prepared features for monitoring. No training, evaluation against ground truth or probability recalibration occurs here.

The System 2–System 3 handoff anticipates the following monitoring needs. System 2 publishes the inputs; System 3 performs the monitoring calculations. In this table, scores.csv, features.csv and manifest.json all belong to s3://customer-churn-pipeline-a81b79/inference/cell2cell/<batch-run-id>/. These are the intended capabilities, not a claim that all are implemented.

Metric / monitoring requirement How it is calculated Input sources
PSI per feature Compare each feature’s reference proportions p_i with current batch proportions q_i using fixed bins or categories: \mathrm{PSI}=\sum_i(q_i-p_i)\ln(q_i/p_i). features.csv contains the prepared feature columns. System 3 supplies the saved reference distributions; customer IDs are excluded.
Score drift Compare the distribution of predicted probabilities with a reference score distribution. The System 2 contract does not specify a statistic or threshold. scores.csv → churn_probability. A reference score distribution must also be supplied to System 3; the batch does not contain it.
Flag rate \text{flag rate}=\frac{\text{flagged customers}}{\text{scored customers}}. For a top-k fallback, report the policy and compare with its expected rate; do not describe it as cost-optimal. scores.csv → outreach_flag; manifest.json → flagged, rows, threshold.outreach_policy, threshold.top_k.
Model quality Join observed labels to the already-decided outreach flags; count TP, FP, FN and TN, then calculate quality metrics on matching customers only. scores.csv → customerid, outreach_flag joined by customerid to a separately supplied churn_label. Labels are not available in the live holdout.
Bias slices Compare flag rates and, when outcomes exist, quality across customer groups. The System 2 contract leaves the particular comparisons to System 3. scores.csv joined by customerid to demographic columns in curated/cell2cell/<version>/split=holdout/; observed labels are additionally needed for group quality metrics.
Baseline per model — reference requirement Associate the reference distributions with the approved model being monitored. This is an identity requirement, not a numeric metric. manifest.json → model_package_arn, execution_id, approved_contract_uri identifies the model in this repo. The team’s contract also specifies an approved-contract checksum; this repo does not use that checksum.

Component analysis

Diagram

Key AWS actors and concepts

A SageMaker Model is a configuration pointing to a model artifact and container image. Batch Transform uses it for a finite inference job; it does not deploy a persistent endpoint. Model Registry supplies approval status, ECR supplies the image, and S3 holds the inputs and outputs.

Sequence analysis

Prepare inputs

Overview

The operator selects an approved contract explicitly. The launcher checks its package is still approved and reads the pinned preprocessing and evaluation report. It loads curated holdout rows and calls the same preprocessing transform used in training, with the saved medians, encodings and feature order. Customer IDs are kept separately. The evaluation must contain a selected cutoff; an older fixed-cutoff report is not accepted.

Artifacts and effects analysis

Versioned processes and outputs

The contract selects the registry package version and fitted preprocessing version. The input comes from the configured curated version. A new batch run ID, independent of the training execution ID, identifies this inference run.

Dataset before and after

All holdout customers are retained, ordered by customer ID. There is no new train/validation/test split. The model input has the pinned feature columns, without a header, customer ID or label.

Run Batch Transform

Overview

The launcher creates a temporary SageMaker Model from the pinned artifact and image, starts one Batch Transform job and waits for completion. AWS reads the feature CSV and writes one raw score per customer. The launcher removes the temporary model afterward. The job uses the existing execution role and instance-type settings; no separate Terraform stack is required.

Artifacts and effects analysis

Versioned processes and outputs

Inference uses the exact pinned model and image. It creates neither a new registry package nor a new model version.

Dataset before and after

One feature row becomes one raw score in the same order. The job does not apply the contact cutoff. Ground-truth labels are unknown, so no confusion matrix or AUC is calculated.

Publish batch outputs

Overview

The launcher joins predictions to the saved customer IDs and sets outreach_flag = 1 when the raw score is at least the pinned cutoff. It writes scores and prepared features, then publishes the batch manifest last. Downstream monitoring reads runs with a manifest and uses the existing outreach flags rather than recomputing them.

Versioned processes and outputs

The batch manifest records the input URI, selected approved contract, training execution ID, model and preprocessing versions, cutoff and outreach policy, row and flagged counts, and transform job name. It is separate from the training execution manifest. The threshold is reused, not selected again.
